Minute V2 · Design Notes
These are design decisions by Franky Farra-Frond, Senior Interaction Designer, i.AI. Each decision is cross-referenced with the GDS Design System — noting where GDS is followed without deviation, where it has been adapted for application context (GDS+), and where an i.AI-specific solution was required. Decisions marked D are settled; Q are open questions (I known issues, listed with open questions; F future features, listed with decisions).
Architecture decisions
D
GOV.UK header added as a full-width persistent bar above all pages — GDS blue (#1d70b8), crown SVG and GOV.UK wordmark on the left, signed-in user email on the right. Added at the request of the strategy team's feedback that the product needed to be framed as an official government application — the header does this immediately and at the highest visual level. Explicitly decided not to include the Minute service name inside the GOV.UK header; the product name belongs to the sidebar, not the institutional header.
D
Transcriptions page fully rebuilt as a proper GDS table — replacing the previous flex-based row layout with semantic HTML table structure. Column order settled as: Select · Title · Date saved · Status · Actions, following the GDS principle that users should read all row information before being offered actions on it. "Rename" column (Jonny's implementation) removed — a column header implies every row has a value for that field, but what was there was a single icon, not a data attribute. Actions moved to the last column with header "Actions", following both the GDS DWP design system explicit guidance ("actions should always be placed in the last column cell") and the MOJ multi-select pattern. Checkbox for row selection placed in the first column, not under Actions — GDS MOJ multi-select is explicit on this; selection and actions are different gestures and conflating them into one column breaks both the interaction model and screen reader table navigation. "Date" column renamed "Date saved" — precision over brevity, removes ambiguity about whether the date refers to recording, saving, or transcription.
D
Sidebar nav item renamed from "Saved" to "Transcriptions" across all five sidebar instances — Jonny's implementation used "Transcriptions" and it was agreed as clearer for users who don't yet know what "Saved" means in this context. Bookmark icon retained — it was the agreed icon for this item and carries the right semantic meaning (save/bookmark a record). This is a label change only, not an IA change.
D
Template editor built — one shared page serving create, edit, and view, for both document and form types, rather than four separate pages for what's structurally the same surface. "Create new template" now genuinely opens it instead of going nowhere; "View" (new, added to every default) opens it read-only — fields disabled, Try an example and Save both hidden, with a line explaining a default can't be edited directly and pointing at Duplicate instead; "Edit" (new, on every custom/duplicated template) opens the same page fully editable. This is the page that resolves both gaps named two turns ago in one move: previewing a default's real content before forking it, and actually editing a template's content at all, which nothing in this file could do until now.
D
"Try an example" actually populates the content field now rather than sitting inert — different content per type, since the two forms genuinely need different example shapes: a structured outline for document templates, a style guide plus two pre-filled sample questions for form templates. The rich content toolbar (B/I/S, headings, list) is decorative, matching the same honesty already established for Review's Edit-mode toolbar — present to show what authoring a template would look like, not wired to real formatting commands.
D
Saving a new template genuinely adds it to the real Templates list — no tag, full Edit/Duplicate/Delete, same as any other custom template — closing the loop from creation through to appearing where it'll actually get used. Editing an existing template currently returns to the list without persisting content changes, since there's no real per-template content storage in this file yet to write back to — name and description do round-trip correctly; content editing is genuinely functional as an interface, just not yet wired to update the underlying row. Viewing a default shows real, written placeholder content per template (not a generic stand-in) so the preview is actually informative, but it's invented for this demo, not the real prompt text behind any of these templates.
D
Two fixes after actually using the editor: the bottom-left button said "Cancel" in every mode, including View — wrong word there specifically, since nothing was being edited to cancel out of. Now reads "Close" in View mode, "Cancel" everywhere something's actually in progress. Separately, the standalone "Rename" button on custom template rows was pure redundancy — clicking the template's name already triggers the identical rename behaviour, a button doing the same thing a second way was never adding anything except width. Removed it from both places custom-row actions get built; every row goes from four buttons down to three without losing any capability.
D
Templates page built. Deliberately one flat list, no Document/Form section split — that distinction is real but belongs to whoever's building a template (the two creation forms genuinely differ), not whoever's picking one, which is the far more frequent action and already correctly lives in the toolbar and the save-confirmation modal. The technical split only appears in the small "Create new template" popover, the one place it's a genuine fork. Matches how Granola and Fireflies organise their own template libraries — by meeting-type name only, never by an underlying technical category the person browsing has no reason to think about.
D
The six existing templates are fixed defaults — Duplicate only, no Delete, no Rename, marked with a "Default" tag. Duplicating one inserts a new row with an empty, focused name field and zero suggested name, deliberately — naming is the user's choice, but the "Duplicated from X" line stays attached automatically regardless of what they call it, so lineage is always visible even when the name gives no hint of it. That same lineage line is the natural place a future "Shared by [name]" tag would also live, once sharing exists — same mechanism, not a new one.
D
Favorites pin to their own section above everything else, toggled by a star — deliberately a different icon from the bookmark already used for "Saved" in the sidebar, to avoid one icon meaning two different things in two different places. The fuller sort menu (alphabetical, most used, by type, most recent) was built now rather than deferred, on the explicit reasoning that this prototype exists partly for user testing, and real accounts will vary far more in template count than this file's demo set of six — "most used" sorts against a hardcoded demo count, since there's no real usage tracking to sort against yet; that's a known, named simplification, not an oversight.
D
Found and fixed a real consistency gap while building Delete for duplicated templates: it initially removed the row immediately, no confirmation — every other Delete in this entire file (Review, Saved, at-risk recordings) goes through a confirmation modal first. Rather than ship the one inconsistent exception, extended the existing shared delete modal to handle template rows too, reading the live (possibly renamed) title rather than whatever name was set at creation time.
D
Fixed a real bug, not a hypothetical edge case: favoriting every template would have left "All templates" sitting as a header with nothing under it, since the empty-state hide logic only existed for the Favorites section, never written symmetrically for All. Added the matching check and call it from every place row counts can change — favoriting, duplicating, deleting — rather than just the one spot that happened to surface it first.
D
Checked Notion's actual duplicate behaviour before deciding whether duplicating a template should open a page, a popup, or stay inline — it duplicates instantly, in place, with renaming and content editing both left as separate, later, optional actions, never forced immediately. That validates the inline duplicate-with-empty-name-field already built here, but also clarifies what's still missing: a genuine way to engage with a template's actual content, which doesn't exist yet for either a fresh duplicate or an existing custom template. Settled on a single shared destination for that, deliberately distinct from Duplicate itself: a "View" or "Edit" action (read-only for defaults, editable for custom templates) opening the real template-content page once it exists — which also resolves the separate "no way to preview a default before duplicating it" gap, since viewing a default's real structure is the same page, just non-editable. Not built yet — the button isn't wired to anything, since wiring it to a page that doesn't exist felt worse than naming the plan clearly and building the real editor next, which is the explicitly agreed next step.
D
Template choice has moved twice and the journey is worth documenting honestly. First built into the "Save this recording?" modal — correct reasoning (Jonny confirmed regeneration is slow, so choose before generation) but wrong moment (the modal is a consequence screen, adding a choice there made it heavier). Then moved again to the Capturing screen, outside the recording card as a detached secondary zone below it, shown in sync with state-capturing and hidden on save or discard. This is the right position: the meeting is still running so you have full context to make a good choice, the window is always proportional to the meeting length (a 60-minute meeting gives 60 minutes, a 10-minute meeting gives 10 minutes — unlike the transcription window which can close in seconds on short recordings), and it degrades gracefully if someone ignores it entirely, defaulting to whatever is checked in name="cap-tpl". The save modal is now genuinely lean: consequence statement, Keep recording, Save recording — nothing else. The Done screen's template switcher remains as an escape hatch for after-the-fact changes, which was always its intended role.
D
Considered, and explicitly rejected, removing Done entirely and jumping straight to Review now that the first generation should usually be correct. Found a close structural parallel worth citing: Fireflies' "Instant Summary" is functionally the same two-tier pattern as Done → "View full summary" — a fast, lightweight result immediately, with a deliberate second click into the heavier full view, specifically because full processing takes longer. Upfront template choice and Done's existence solve two different problems — one fixes whether the content is right, the other gives a low-commitment landing point before committing to Review's heavier shell (sidebar, toolbar, full editing surface). "Record another meeting" living on Done specifically, rather than only reachable from Review, was the concrete cost identified for removing it — back-to-back recordings would otherwise require navigating out of a document-heavy page first, every time.
D
Sidebar items settled into one explicit rule rather than case-by-case judgment: global (exists independent of any specific recording — Saved, Templates, future Help/Tour) vs. contextual (only meaningful inside a specific document — Summaries, Transcript). Global items get permanent slots and no category label, since each is self-explanatory on its own; contextual items only render at all once their context exists, and a label is only earned by genuine sub-structure underneath it. Concrete results of applying that rule: "Menu" dropped from all three sidebar instances (Saved/Templates don't need a wrapping label any more than Summaries/Transcript's category needed "Document"); "Document" dropped from around Transcript for the identical reason, already settled once for Transcript specifically and now generalised into the actual rule it was an instance of. Saved and Templates picked up icons, matching the icon-consistency pass already done on every toolbar in this file — the sidebar's global items were the one remaining icon-less spot. Templates' own internal "Document templates / Form templates" split (seen in the live product) deliberately stays inside that page's own content, not duplicated into the sidebar — that sub-structure exists for switching between sub-workspaces once you're already there, not for jumping between them mid-task elsewhere, which is the actual reason Summaries' sub-structure does belong in the sidebar.
D
Found and fixed a real structural bug right after this page first shipped: it rendered entirely blank when opened. Cause was a nesting error, not a display-logic error — the new page had been inserted nested inside #page-review's own subtree rather than as its sibling, so it was a descendant of a display:none ancestor that was never being shown at the same time. Setting its own display to block did nothing while its parent stayed hidden. Confirmed this was the cause by tracing actual div depth rather than guessing, then moved the page — and the shared Delete modal, which had the identical problem — to true sibling level. Also fixed in the same pass: the Delete confirmation's heading and "Keep" button said "transcription" even for an at-risk recording that isn't one yet — now reads "Delete this recording?" / "Keep recording" specifically for that case, "transcription" everywhere else.
D
"Not yet saved" reordered to sit below Search/Filter rather than above it, and switched from a bordered card to a plain warning-tinted background with no border. Reasoning behind both: search and filter are relevant on every single visit regardless of anyone's at-risk status, while the callout is conditional and often won't be present at all — the universally-relevant control earns going first. The bordered-card treatment was also a stronger visual claim than the content needed; a flat tint stays visible without reading as an alarm competing with the page's own title.
D
Pagination added to the saved-transcriptions list — this closes a gap flagged as far back as the original flow-architecture document, before any of this redesign work started: the list "works fine at 2 items, will not work at 50." Three more demo entries were added (five total) specifically so pagination has something real to page through rather than sitting permanently disabled — Previous/Next and the page count recalculate live whenever a row is rescued from "Not yet saved" or deleted, rather than being fixed at page-load. Search and Filter remain visual-only, not wired to real filtering — that's a separate piece of work, not done here.
D
"Most recent first" removed entirely — carried over from the live product without re-deriving whether it earned its place here. It asserted something the dates already show: a list running 11 June down to 2 June is self-evidently newest-first without being told. Filter (All / Expiring soon) kept, since it solves something genuinely distinct from search or pagination — finding the ones about to expire without hunting by eye across pages — but rebuilt from a native select (the one control on this page that looked like a different product, visibly OS-chrome in a screenshot) into the same chip-and-menu pattern already used for Retention, History, and Hide speaker tags.
D
Real bug, not a styling miss: --text-warning and --bg-warning were referenced throughout the at-risk callout and the "Expires in…" labels from the moment they were first written, but never actually defined anywhere in this file's own :root block — they were carried over from memory of a broader token system this file doesn't itself include. background isn't inherited, so the missing --bg-warning resolved to fully transparent — the callout's tint was never rendering, at all, since it was introduced. --text-warning is inherited, so that one failed more quietly, silently falling back to whatever ambient text color surrounded it rather than visibly breaking. Both are now defined directly in :root. Swept every other var(--…) reference in the file against the actual defined set after finding this, specifically to check whether the same mistake existed anywhere else uncaught — it didn't.
D
Search and Filter pulled apart with justify-content: space-between rather than sitting adjacent with a small gap — sitting close together implied they were one combined search-and-filter unit, which isn't true; filtering by "Expiring soon" has no dependency on what's typed into search. Search's placeholder shortened from "Search your transcriptions" to "Search transcriptions," and the input itself narrowed from filling all remaining space to a fixed width, since it no longer needs to visually anchor the filter chip beside it.
Q
Clicking "Saved" in the sidebar mid-recording navigates away immediately, with no confirmation — unlike the logo, which is explicitly guarded against losing an active recording. Not an oversight being hidden, a genuine inconsistency not yet resolved: if the logo deserves that guard, the same risk arguably applies to any nav item capable of leaving Home while Capturing is active, not just the one currently wired for it.
D
V2 — this file's defining change. A persistent sidebar now exists on every page, including Home, Capturing, and Done — not just the review page. The logo moved into the top of the sidebar itself, RevenueX/Notion/Linear-style, rather than sitting in a separate header bar; there's no header bar left anywhere in this file. The global Menu section (Saved, Templates, Settings) sits at the top of every sidebar instance; on the review page it sits above the existing document-specific Summaries/Transcript section, so global and contextual navigation are visually separated rather than mixed into one undifferentiated list. Chosen over a consolidated header menu (the lighter alternative discussed first) specifically on accessibility grounds: a visible, persistent list needs no icon to be recognised, no hidden-menu keyboard/ARIA behaviour to get right, and no extra cognitive step of "what does this icon represent" — all real, non-hypothetical risk for a persona this exploration has repeatedly flagged uncertainty about regarding interface-convention familiarity. Static for now, not collapsible — explicitly left open as a future option if the permanent width turns out to cost more than expected on Home, Capturing, and Done specifically, where the original design was deliberately compact.
D
New transcription page removed entirely: starting a recording happens on Home now. Idle, Capturing, Processing, and Done are one state machine on one page, not four separate page navigations.
D
No method is visually promoted on the Idle screen, unlike the live product's "Most used" card on in-person/audio. Analytics confirmed virtual (40%) and audio (37%) are close enough to call a toss-up, with upload at a real 19% — not negligible enough to relegate.
D
Document review is a genuine separate page, not a fifth state of Home. Real document review needs more room than a quick-decision panel — sidebar-plus-main-content shell instead.
D
Global nav (Saved / Templates / Settings) kept visible on the review page after an earlier draft dropped it — blocking those without returning Home first would block a plausible task.
D

Fixes a real ambiguity Franky hit in testing: with the sidebar previously starting below the title row, Delete's scope (the whole record) wasn't visually distinguishable from "delete the thing in the list below." Matches Confluence's actual structure, not just the general idea of one.

Type scale doctrine — size carries control class, because colour cannot (Franky's note, reasoning now recorded). An earlier note logged that chips are smaller than buttons; this note records why, which is the load-bearing part. In a GDS-constrained palette, colour is a scarce channel already spent on semantics — danger red, accent blue, status tags, warning tints. If colour also had to signal control class (button vs chip), the two jobs would collide: a red chip and a red button would falsely claim kinship. So class is carried by size and padding, leaving colour free to mean things — and the distinction satisfies WCAG 1.4.1 (Use of Colour) because it survives greyscale and colour-blindness. The fixed scale, so this stays a system rather than per-component taste: 13px = buttons and table content; 12px = chips and table metadata (dates) — chips sitting on the metadata rung is semantically honest, as chips are metadata-weight controls; 11px = tags. Two guardrails: 12px is the floor for anything interactive, and chip padding stays generous so the reduced type never reduces the hit target.

Tone of voice — app-wide content doctrine. Agreed direction (Franky + Jonny): cohesive, generic, institutional — this is a government application used by civil servants, and authority comes from staying neutral, not personalised. The working rules: (1) instructions are imperative and verb-first — "Choose how to capture this meeting", "Select a template", "Add discussion points" — never "You will…" or "You can…" framings; (2) consequences and system behaviour are stated in neutral present tense — "are permanently deleted", not "will be permanently deleted"; (3) second person is reserved for system state only ("Your current data retention period is set to 90 days") and used sparingly — GDS itself uses "your" for state, and purging it entirely produces the passive bureaucratese GDS warns against; (4) the app never says "we" and carries no personality, reassurance padding or exclamation. Why it matters: consistency of voice is itself a trust signal — copy that switches register between screens reads as unowned; and verb-first imperative is GDS content style, so the doctrine strengthens rather than strains the compliance story. Applied in this pass: speaker-rename note and template-editor subtitle rewritten to the doctrine; new Settings and Generate modal copy written to it from the start. Remaining copy to be audited against these four rules as screens are touched.

Standing explanatory copy — the trade-off named, and why we don't add it by default. There's a real cost on both sides: a first-time user benefits from a line explaining what a feature does; a returning user pays for that same line every single time, forever, whether they need it or not — and permanence is the part that makes it expensive. Position held throughout this redesign: it's acceptable for a feature to take a moment to work out. A short pause of "what does this do" from a first-time user costs less than a page that has quietly taught every returning user to skim past explanatory text altogether — which is exactly what happened to the old Minute. Its interface carried standing explanatory copy on nearly every feature, and the result wasn't clarity, it was noise: so much permanent explanation that none of it got read, including the explanations that actually mattered. That failure is the origin of this decision, not the survey response that later confirmed it. Scope, stated precisely so it can't be misapplied: this covers only correctly-labelled, working features that are simply underused or undiscovered — never a reason to leave a broken, missing, or genuinely unclear label unfixed. Those are bugs, not learning curve, and get fixed directly (see QW3 — no way to compare templates, fixed with a link to the Templates tab — and CD2 — the Type column read "Summary" where a user expected "Default", label corrected). CD3 is the different case, and worth being precise about it: it directly asks us to explain what templates are, or remove them if we won't. That is exactly the standing-explanation ask this decision holds against — CD3 is not filed alongside QW3/CD2 as a fixed label, it is the concrete example the position above is written to answer. Where the line sits case by case: a feature earns explanatory copy when its consequence is destructive or hard to reverse (the delete-scope precedent), or when it depends on the platform for something the interface alone can't convey (see Show/Hide references, which needed one line the first time, not a paragraph every time). A feature that's simply underused — like Duplicate template, raised separately — is a discoverability problem, and the fix is better labelling and placement, not a sentence explaining it.

Someone working the same kind of meeting repeatedly can end up with several records that read identically, and picking the wrong one then is a design failure, not a user failure — an incident in another government transcription product, where content from one case was copied into another's court material, was traced back to exactly this. Behaviour: wherever a title can be set, the candidate is checked live against the user's other records and, on a match, a message names the record it resembles and its date. The user keeps the title or changes it; nothing is prevented, which matches how the rest of Minute treats AI output. All matches are reported, not the first: the message leads with the count when there is more than one ("3 records already have a similar title"), lists up to three with their dates, and says "and N more" beyond that. The count is the signal — "you have four of these" is a far stronger prompt than "one exists", and the whole problem is several records sharing a title, so naming one would understate it. Three places, one check: the inline rename in the list, and the title field in both review edit states. The record being edited is excluded from its own comparison. Form: GDS Warning text — warning icon, bold lead, plain sentence — because this is a caution, not an error; it sits directly beneath the field and announces via role="status" rather than alert, since it is advisory. Copy: "Similar title already exists. "X" — date. Keep the title if this is the same meeting again, or change it so the two can be told apart." It states what was found, names both legitimate outcomes, and leaves the decision where it belongs. Defaults chosen for the open questions, and why: Scope is the user's own records — comparing across an organisation means reading other users' titles, which is a data-protection question with different owners. Lookback is every record in the list, which retention already bounds to the deletion window, so no separate time limit is needed. Where is at the point of editing, not in the list: the moment a title is being set is the moment it can still be changed. Thresholds: titles are normalised (case, punctuation, spacing) and count as a repeat if identical, if one is the other plus a tail of twelve characters or fewer (a date, a number, "follow-up"), or if bigram similarity is 0.8 or above. Tested against the current records: exact and near-exact pairs fire; unrelated titles do not; "Planning Committee Pre-Meeting Briefing" against "Planning Committee" correctly does not.

Live keeps summary versions in a dropdown that exists only while editing: people cannot see which version they are reading, cannot look back without entering edit, and cannot see what versions exist until they open it. A meeting has one date: the day it took place. Recordings made in Minute are dated by the recording; uploads ask for it; the record lets you change it. The live product dated every record, and every summary, by when it was created, so a recording uploaded today of last week's meeting read as today's meeting, and templates wrote that date into the summary as the date the meeting took place. One date. The list's Date column, its sort order, the sidebar, the identification block above the transcript and each summary, and the delete confirmation all use the meeting date. The upload date stays behind the scenes, for retention and audit. Where it is asked. Only for uploads, in "Upload a recording", next to the file: "When was this meeting?", a GOV.UK date input, required, prefilled with the date the file was last changed, with a hint to check it. In person and virtual recordings are not asked: Minute recorded the meeting, so it knows when it happened. "New summary" on a record does not ask either: it is the same meeting, and the date belongs to the record, not to one summary. No "provide no date". Anyone uploading a recording knows roughly when it was, and a missing date brings back two dates in the list. Errors follow the GOV.UK date input: "Enter the date of the meeting", "Date of the meeting must be a real date", "Date of the meeting must be today or in the past", shown in the reference inline error and above the fields. Changing it. "Change the meeting date" in the record's options menu, beside the title. The identification block and the sidebar update straight away, and screen readers are told the new date. The summary does not write the date. It is shown above the summary from the record, so an edited date is right everywhere; text a model has already written cannot update. A date and a time. The system holds one timestamp per meeting, so the question asks for both: the GOV.UK date input (Day, Month, Year), then one Time field with the hint "For example, 14:30 or 2:30pm", prefilled from when the file was last changed. The Time field accepts the common ways of writing a time (14:30, 14.30, 2:30pm, 2pm) and Minute shows it back on the 24-hour clock, as everywhere else in the product. A bare "2" is not accepted, because it could be 2am or 2pm. Shown as one line first.
